## 1. 产品概述

### 1.1 一句话定位

> **投票把时间定下来，日历把事情管起来——点卡片就能投，定档自动进群日历，下次照这场再约。**

### 1.2 设计哲学：心理引擎表

本产品是协作工具，不是情感仪式——引擎不靠"攒福气"，靠**"被需要感 + 当家做主的面子 + 群里有安排"**：

| 引擎 | 心理机制 | 对应设计 |
|---|---|---|
| **组织者面子引擎（主引擎）** | 张罗事的人要的是"这事能成，且成在我手里"的功劳感；没人为工具发起活动，人为"当把事张罗成的那个人" | 定档卡片署名（`球局定了！周六下午 · 王哥组织的`）；发起人战功沉淀（本周组织 2 场）；定档盖章仪式（发起人的收口动作） |
| **搭把手引擎（参与引擎）** | 群友的最大阻力是"麻烦"；顺水推舟帮个忙的心理成本为零，被点名催促的心理成本极高 | 参与动作全部点选化（≤2 次点击）；认领按钮写「我来」而非「领取任务」；催办文案全走召唤语气（见下） |
| **围观引擎（传播引擎）** | 数字会动的卡片自带围观欲；"还差谁"清单有天然的补位冲动 | 卡片实时计数（`已投 5/9 人`）；空缺事项虚线框 +「我来」按钮——空缺本身召唤补位 |
| **确定感引擎（留存引擎）** | 群最怕的不是没约成，而是约成后信息散在聊天记录里、下次又从零开始 | 定档自动写入群日历；日历顶部先看「接下来」；历史活动可一键「照这场再约一次」 |

**质问感 → 召唤感的文案红线**（引擎层约束，全部功能共用）：催办、提醒、催填的话术永远从"群体需要你"出发，禁止从"你欠群体"出发——「还差你的那份」❌（质问）→「这场还缺个人搭把手」✅（召唤）；「就差你了」❌ →「周六的位置给你留着」✅。催的频控（每日 ≤1 次）与语气共同构成"永不惩罚用户"的群内版本。

### 1.3 要解决的问题

微信群是中文互联网最高频的协作场所，但群的协作工具一直很难用：

| 用户侧痛点 | 现状 |
|---|---|
| **约个时间全靠刷屏**：「周五晚上行吗」「我周五不行，周六呢」「周六下午我有事」——组织者人肉对齐所有人的档期，聊三天定不下来 | 微信没有任何结构化凑时间工具；市面上的投票小程序全是单选刷票/拉票营销逻辑（宝宝投票类），没有一个把"多人多选可用时间 + 自动找最优解"做好的 |
| **拿主意七嘴八舌**：吃什么、去哪玩、看哪场，接龙式各说各话，最后还是群里嗓门大的说了算 | 无轻量、实名、见头像的快速表决工具 |
| **事情定完就散**：上次哪天打的球、下次谁还来、这个群最近有没有活动，全靠翻聊天记录 | 微信没有群维度的轻量日程资产；个人日历无法承载"我们群"的集体记忆 |
| 想用机器人，但普通微信群拉不进任何机器人 | 工具类需求全部靠"人肉" |
| 高情商回复：不知道怎么回领导/长辈/相亲对象 | 用户去 ChatGPT 类产品来回切换，先截图再描述再复制，链路太长（迁主体后接入，D4） |

### 1.4 产品哲学：群即入口，卡片即界面

本产品的一切设计围绕一条主链路：

```
群主在小程序里发起时间投票 → 分享卡片到群 → 群友点卡片直接参与 → 最优时段高亮 → 组织者定档 → 定档卡片回群 + 自动写入群日历 → 日历承接下次发起
```

五个关键判断：

1. **微信小程序的命脉在"群"**：群内高频、协作、传播三要素齐备。单人工具靠留存，群工具天然靠裂变——每一次参与都是一次新用户的进入。
2. **卡片是唯一传播载体**：小程序无法主动往群里发消息（见 §3 能力边界），所以每个功能都必须设计出一张"值得发回群里"的卡片。**分享卡片不是增长手段，是产品本体。**
3. **投票负责获客，日历负责留存**：时间投票是原生空白，解决"这一次什么时候"；群日历把定档结果变成"这个群的安排"，解决"下一次别从零开始"。两者是同一条主线的两次价值交付，不是两个并列功能。
4. **单次工具没有护城河，群资产才有**：投票记录、到场名单、常用时段、活动模板沉淀在群维度后，换组织者也能继续用；这是竞品做拉票工具时不会积累的数据。
5. **AI 是增强层，不是主线**：投票与日历不依赖 AI 也成立；AI 回复是拉新钩子，但**个人主体不可做（决策 D4）**，移至迁移企业主体后接入。

**产品叙事：定时间 → 管事情 → 凑人头 → 凑分工。** 组织任何一件群活动，都会经历同一条链路：

```
定时间（投票）→ 管事情（群日历）→ 凑人头（收集填表）→ 凑分工（群待办）
```

每个环节的产出是下一环节的输入：投票输出定档时间与到场名单，日历输出群节奏与可复用活动，收集输出报名底册，待办输出分工结果。产品从"投票工具"的印象逐步长成"组织任何事都用它"——护城河是群资产，不是单个功能。Roadmap 按此叙事展开（§11）。

**群协作信任三原则**（机制层统一规范，全部功能共用，每个交互设计都要过这三关）：

1. **实名**：所有参与/认领/记录都实名见头像——群协作的信任靠实名，openGid 群内数据本就是公开信息；这也是防刷的根基（openid 一人一票，无需登录墙）
2. **可改不可逃**：档期会变、认领会黄，所以投票可改票、待办可转让、填表可改填——但**不许悄悄消失**（无"退出不留痕"设计，放回池子=全群可见）
3. **永不惩罚**：不设扣分/降级/逾期红点；催办走召唤语气 + 频控（每日 ≤1 次）——"永不惩罚用户"从福签一脉相承，工具版本 = 不制造任何社交压力反转

### 1.5 北极星指标

**每周活跃协作群数（Weekly Active Groups, WAG）**：一周内至少产生 1 个「有 ≥3 人参与的活动」的群数量。

它同时衡量：
- 留存（同一个群反复发起活动 → 群级留存）
- 传播（每个新群必然来自一次分享）

MVP 实验期（100 群 × 1 周）的三个验证指标（详见 §9）：
- **分享率**：参与活动的新用户中，向群里再次分享任意卡片的占比
- **日历回访**：参与或查看定档结果后，回访群日历的用户占比
- **复约率**：定档活动后，同群在 14 天内再次定档的比例

### 1.6 差异化：凭什么微信里"投个票"要用你？

这是本产品必须回答的第一个尖锐问题。现有投票小程序的真实格局：头部产品全部服务**营销拉票场景**（萌娃评选、商家活动），广告重、要求授权手机号、匿名可刷——**协作场景根本没人做**。差异化三层：

| 层 | 微信原生/竞品现状 | 本产品 |
|---|---|---|
| 凑时间（核心壁垒） | 完全空白。各说各话刷屏对档期 | 多选可用时间 + 每个时段自动聚名单 + **最优时段高亮**，一键"定这个时间" |
| 表决体验 | 原生无；竞品要登录、有广告、匿名刷票 | 点卡片即投、实名见头像、可改票、零登录零广告 |
| 汇总回流 | 结果只存在于聊天记录里，翻不到 | 结果沉淀小程序可回看；定档自动进群日历，历史活动可一键再约（第二次传播 + 长期回访） |

**明确不做的投票场景**：不做匿名拉票、不做刷票助力、不做营销评选。这既是产品定位（协作工具，不是营销工具），也是合规减负（营销拉票类是内容审核与诱导分享的重灾区）。

一句话：**竞品把投票做成了拉票工具，我们把投票做回它本来的样子——一群人快速商量一件事。**

### 1.7 产品名（命名 = 搜索词策略，两级结构）

命名规则（prd-optimizer 〇.5-4 + 自检第 7 条）：**名字里必须有功能搜索词**（用户搜「投票」「接龙」不搜品牌名；分享转化后的二次搜索全靠功能词承接）**+ 品牌词过好奇心测试**（描述性命名"XX助手/XX管家"是禁忌）。结构 = `{功能词} + {品牌词}`，参考实战先例「慢邮纪念日」。

**搜索词矩阵**（名字至少含 1 个，简介全量埋一遍）：
- 投票（最强功能词——用户真实搜索词，非品类词"群协作"）
- 凑时间 / 定时间 / 接龙（长尾，进简介）

| 候选 | 结构拆解 | 搜索能力 | 好奇心/记忆点 | 风险 |
|---|---|---|---|---|
| **「咦投票」（推荐）** | 品牌词「咦」+ 功能词「投票」 | ✅ 直接命中最大搜索词 | 「咦」制造"这是什么"的缺口；群里发卡片配文「咦，投票？」自带传播梗 | 拟声词可能显轻佻，中老年群接受度需验证 |
| 「投票就现在」 | 功能词「投票」+ 品牌词「就现在」 | ✅ | 号召感强 | 略口号化，5 字偏长 |
| 「凑个局」 | 场景词（无硬功能词） | ⚠ 弱——需简介补投票/接龙 | 直指组织场景，有口语感 | 功能词缺失，二级搜索承接差 |

**决策**：推荐「咦投票」，但**名字上线前必须在公众平台后台查重**，查重被占则顺位「投票就现在」；无论哪个，「简介」必须完整埋入关键词矩阵：`投票 / 凑时间 / 聚会定时间 / 分工 / 接龙 / 收集报名`——简介是搜索权重的第二入口，比名字能埋的词多。

**分享卡片标题三段式模板**（全功能共用）：`{悬念/缺口} + {数字动态} + {组织者署名}`——如 `就差 2 个了！周六球局 7 人有空 · 王哥喊你来`；落地页直达投票/待办场景（不落通用首页，已达标）；卡片文案带品类词（"投票"），承接转发后的二次搜索。

## 2. 目标用户与核心场景

### 2.1 用户画像（心理诉求标准句式："想 __，但 __"）

- **组织者（王哥，34，公司行政/班级家委会/球局群主）**：**想把聚会张罗成，但每次对档期、催人都要在群里刷屏三天，事成了功劳也没了只剩累**。他要的是"这事轻松办成了，且大伙儿知道是我办的"。**他是产品的发动机**——一个人带来 30 个群成员；服务好他 = 服务好一个群。
- **顺水推舟型群友（小李，28，普通群员）**：**想搭把手做个靠谱的人，但任何要下载、要注册、要打字的"举手之劳"都嫌麻烦**。他要的是点开卡片、点两下、完事——参与成本必须低于"在群里回一句+1"。
- **发起人候补（琳琳，26，上次被王哥喊去帮忙统计的群员）**：**看懂了这套玩法、自己也想在自己别的群张罗一回**。她是病毒链路的 V3 转化目标：体验过"被服务"，下一步想"当发起人"——详情页常驻「我也发起一个」就是为她设计的。

> 画像变更：v1.2 前的"社恐型（小陈）"画像随 AI 回复移出 MVP（D4）一并移除；其画像位由"发起人候补"替代——她才是 MVP 病毒公式里缺的那一环。

### 2.2 核心场景

| # | 场景 | 频次 | 病毒系数来源 |
|---|---|---|---|
| S1 | **聚会凑时间（主战场）**：王哥想约球局 → 发起时间投票（周五晚 / 周六下午 / 周日晚）→ 卡片进群 → 大家点选自己有空的时段 → 「周六下午 7/9 人有空」自动高亮 → 王哥一键定档 → 结果卡片回群，到场名单沉淀 | 每周/群 | 每个投票者都会围观结果；定档卡片是全群触达 |
| S2 | **群里看安排**：定档后自动进群日历 → 群友回看「接下来有什么安排」→ 历史活动一键再约 | 每周/群 | 日历是回访入口；周计划卡与月度战功卡提供第二次传播 |
| S3 | **拿主意（v1.2）**：吃什么、去哪、看哪场 → 单选投票快速表决 | 低频/群 | 与时间投票共用卡片底座，横向扩展组织场景 |
| S4 | 不会回消息（v2.x，迁主体后）：把对方消息粘进来 → 选语气 → 一键复制回微信 | 日常/人 | 单人使用，低传播，但拉新钩子强（"你用的什么小程序这么会说话"） |

**S1 的完整故事线（本产品的黄金链路）**：

```
发起时间投票 → 群友多点选有空时段 → 最优时段高亮 → 组织者定档
→ 定档时段的投票者自动成为「到场名单」→ 名单直达收集填表 / 群待办
→ 定档自动写入群日历 → 活动结束沉淀群节奏（常用时段 / 常来的人）
```

投票不只是投票，它是后续一切协作的**人员底册**——**整条链路里用户只做点选，所有汇总由系统完成**。资金相关（收款）一律交给微信原生「群收款」，本产品不碰。

## 3. 微信生态能力边界（设计前提，所有功能不得违背）

这一节是本 PRD 的地基。**产品的形态由微信开放能力决定，先明确能做什么、不能做什么，再谈怎么设计。**

### 3.1 不能做的（硬约束）

| # | 约束 | 影响 | 对策 |
|---|---|---|---|
| C1 | **小程序无法主动向群聊发送任何消息**。不存在"群机器人"，不能监听群、不能往群里推结果 | 产品不能做成"机器人助手"形态 | 所有触达走两条路：① 用户主动分享卡片回群；② 订阅消息（需用户提前订阅，一次性一条） |
| C2 | **无法读取群聊内容**。微信不向小程序开放聊天记录 | "群聊总结"无法自动完成 | 群聊总结已永久移出产品规划（复制粘贴导入路线交互损耗大，见 §4.2） |
| C3 | **个人主体小程序不能开通微信支付**；即使企业主体，代收代付也涉及资金合规（二清风险） | 资金类功能不可做 | **资金协作功能已彻底砍除（D5）**：收钱场景微信官方「群收款」已覆盖，本产品全线不碰资金相关功能；C3 从设计约束降级为天然边界 |
| C4 | 分享卡片**只能由用户在页面内主动触发**（右上角菜单或页面按钮），不能自动弹、不能利诱强制 | 诱导分享是审核红线 | 分享永远有明确利益（结果卡片对全群有用），但功能不依赖分享解锁 |
| C5 | 一次性订阅消息**每订阅一次只能发一条**，长期订阅消息仅限特定类目（政务民生等） | 投票"截止提醒"、日历"活动提醒"有触达预算 | 每个活动在关键动作（投票/分享/查看日历）时顺滑请求订阅，攒次数；触达文案基调见 §1.2，频控见 §10 |
| C6 | 无法获取群名（openGid 只是加密标识，接口不返回群名称） | 群维度页面不能自动显示群名 | 首次在群内打开时引导用户给群起个备注名（一次输入，全群共享） |

### 3.2 能做的（核心杠杆）

| # | 能力 | 用法 |
|---|---|---|
| E1 | **分享卡片可携带群标识（openGid）**：用户点开群里分享的卡片进入小程序，可通过分享票据机制解密得到 openGid，从而知道"这个活动属于哪个群" | 群维度数据聚合的根基：同一群的所有活动归到一起，群首页可沉淀"这个群的历史活动" |
| E2 | **点卡片即静默登录**：通过云托管 `X-WX-OPENID` 注入获得身份（复用现有 backend 鉴权链路），用户零感知登录 | 参与门槛为零：点开 → 点选 → 完成。**openid 即身份，天然一人一票，防刷不靠任何登录墙** |
| E3 | 分享卡片支持**自定义封面图、标题**（含动态数据如「已投 5/9 人」「最多人选周六下午」） | 卡片是产品本体：数字会动的卡片自带紧迫感和围观欲 |
| E4 | 用户昵称头像可授权获取（含灰色兜底：不授权则用"微信用户+编号"） | 投票名单与票数展示需要 |
| E5 | 小程序可被收藏、可固定到"我的小程序"，微信下拉入口可直达 | 给高频群主做"工具常驻"心智 |

> ⚠️ **openGid 是本 PRD 的最高技术风险，不允许只按乐观路径设计**。分享票据获取群标识的接口形态在近两年基础库有调整（`getShareInfo` → 新票据机制），W1 技术方案必须先做真机验证，并按三档兜底：
>
> | 验证结果 | 产品形态 | 设计约束 |
> |---|---|---|
> | 稳定获取 openGid | 完整群日历：同一群的定档、历史、节奏都挂在群维度 | 群备注名仍由用户设置，不依赖群名接口 |
> | 完全拿不到 openGid | 活动维度日历：以 activity_id 聚合「这一场的定档、名单、历史」 | 首页不承诺"群主页"；分享卡继续携带 activity_id |
> | 部分场景可获取 | 活动为主、群为增强：能挂群的展示群日历，不能挂群的保留活动历史 | 所有群维度能力必须有活动维度降级路径，不得阻断主链路 |

### 3.3 与本项目现有基建的复用关系

- **部署必然独立**：微信云托管环境绑定 AppID——`wx.cloud.callContainer` 与 `X-WX-OPENID` 注入仅在同 AppID 环境内生效，新小程序必须新建独立云托管环境与部署实例，"一套后端服务两个小程序"在架构上不成立（代码组织决策 D3 的前提）
- 代码组织（决策 D3，详见 §13.1）：同仓平级隔离——`miniprogram-group/`（新 AppID）+ `backend-group/`（独立 Spring Boot 应用）+ `api/group/openapi.yaml`（契约 SSOT）；基建走「复制」而非抽象：Dockerfile、`CloudEnvPostProcessor`、openid 静默登录模式、`request.js` 双通道均复制改造，不做 Maven multi-module
- 云托管底座链路（`X-WX-OPENID` 静默登录、MySQL、容器 80 端口部署）已在福签产品验证，`backend-group/` 直接复制沿用
- 开发流程沿用 **fe-be-contract-harness 契约驱动模式**（OpenAPI 契约为 SSOT，先改契约再实现，Stage checkpoint + `contract cli live` 校验）；不走 rocky-harness 流水线

## 4. MVP 范围

### 4.1 范围定义

| 优先级 | 功能 | 理由 |
|---|---|---|

| v1.3 / v1.4 | 收集填表 / 群待办 | 链路延伸，见 §11；均个人主体可做，仅按数据依赖排序 |

> 范围决策说明：① v1.0 曾将群接龙列为 P0，v1.1 移出——微信原生「#接龙」已满足基本报名需求，替代价值薄；接龙以「收集填表」的最简模板形态回归（§11）。② AI 回复原定 P1，因 D4 合规结论移出——它不参与"100 群 × 1 周"实验的核心假设验证。③ 单选投票从 v1.0 后移到 v1.2（D6）：时间投票 + 日历是同一条主线，先打透；单选是横向扩场景，不是闭环必需。

### 4.2 MVP 明确不做（Negative Scope）

- ❌ 不做任何资金相关功能（D5；真实代收本就违规，C3）
- ❌ 不做匿名投票、刷票助力、营销评选、宝宝投票类场景（产品定位 + 审核减负，见 §1.5）
- ❌ 不做群聊总结（**永久移出**：C2 约束下只能"复制粘贴导入"，交互损耗大、价值/成本比不成立，2026-09 评审决定）
- ❌ 不做账号体系/手机号（openid 即身份，一切为了零门槛）
- ❌ 不做消息群发类触达（受 C1/C5 约束）
- ❌ MVP 不做小时级时间、地点推荐、跨群社交、AI 生成内容（见 §4.1 / D4）
- ❌ 不做红包/抽奖等资金敏感玩法
- ❌ 桌面端/React 演示页（本项目 `frontend/` 模式不复制）

## 5. 功能详述 · v1.0 时间投票与基础群日历

### 5.1 功能概述

组织者发起时间投票 → 分享到群 → 群友点卡片进入，点选即投 → 实时汇总、最优时段高亮 → 组织者定档 → 定档卡片回群并自动写入群日历。

v1.0 只做时间投票。单选投票与时间投票共用活动、参与者、分享、汇总底座，但后移到 v1.2（决策 D6）；先把「约时间 → 定档 → 进日历 → 再约一次」这条闭环打透。

### 5.2 类型 A：时间投票「大家凑时间」（主战场）

**本质是多人多选可用性聚合（Doodle 模式），不是计票**——这是交互复杂度所在，也是壁垒所在。

#### 5.2.1 创建流程（组织者视角）

1. 首页点「发起投票」→ 选「凑时间」
2. 填标题（必填，≤30 字，如「下周球局，大家哪天有空？」）
3. 选候选时段：
   - **快捷选择**（默认）：顶部用「本周 / 下周」分段控件切换，只展示当天以后的半天粒度时段——「周五晚上」「周六上午」「周六下午」「周六晚上」「周日上午」「周日晚上」…
   - **默认预选 3 个推荐时段**（如周五晚上、周六下午、周日上午），组织者可直接删减；选项越少，群友越敢投
   - **自定义**（选填）：日期 + 时段（上午/下午/晚上），可加到任意日期
   - 粒度锚定「半天」，**MVP 不做到小时级**——小时级输入成本陡增，而聚会场景"周六下午"通常就够；技术方案中数据模型预留小时粒度字段
   - 候选时段 ≤ 8 个（超出引导删减——选项越多参与率越低）
4. 常用活动模板一键带入：球局、聚餐、爬山、桌游——标题、候选时段、活动备注一起预填；模板只做静态预设，v1.1 再基于群历史升级为群节奏建议（规则化推荐常用时段，不涉及 AI 生成）
5. 创建前展示**分享卡片预览**（标题、主视觉、动态计数占位），让组织者在发出前确认"这张卡值得发"
6. 点「创建并分享到群」→ 触发 `onShareAppMessage`，组织者选择目标群
7. 分享卡片标题动态化：`「下周球局 · 已投 1 人」`

#### 5.2.2 投票流程（群友视角）—— 本产品的生死页

路径要求：**从点卡片到完成投票，≤2 次点击 + 1 次确认；全程零键盘输入。**

```
点开群里卡片
  → 进入投票详情页（已看到标题、全部时段、每个时段当前有谁）
  → 逐个点亮自己有空的时段（可点多选）      ← 点选交互，大色块 88rpx+
  → 点大按钮「就这些时间我有空」            ← 确认，完成
  → （可选）点「分享到群」                  ← 分享按钮常驻
```

体验硬规范：
- 时段色块必须是"点亮/熄灭"的强反馈（色块变实色 + 微震动），选中的愉悦感是参与率的发动机
- 提交后反馈即时可视化：自己的头像飞入每个所选时段的名单（≤1s 动画，可跳过）
- **可改票**：截止前随时重新点选再提交，覆盖旧选择（档期本来就会变，改票是真实需求）
- 已投票者再次进入：色块预亮旧选择，按钮变「改一下我的时间」
- 截止时间到达（若组织者设了）：所有操作锁定，只可查看

#### 5.2.3 结果聚合（投票的核心价值，组织者视角）

详情页每时段一行：

```
┌──────────────────────────────────────┐
│ ★ 周六下午        ██████████ 7 人    │ ← 最优时段：描金边 +「最多人有空」徽标
│   （头像…头像… +2）                   │
│   周五晚上        ████ 3 人           │
│   周六上午        ██ 1 人             │
│   周日晚上        ████ 3 人           │
└──────────────────────────────────────┘
```

- 自动高亮票数最多的时段（并列时全部高亮，组织者自行判断）
- 点任意时段展开该时段的完整名单（头像 + 昵称）
- 顶部汇总条：`已投 6 人 · 9 人看过卡片 · 周六下午最多人有空`。分母只统计群内打开过卡片的去重用户，提示组织者还有多少人没投；不在群内的自然访问不计入分母，避免制造虚假紧迫感

#### 5.2.4 定档（投票的收口动作，第二次传播触点）

定档操作固定在页面底部，主按钮随选中时段变化：先点选某个时段，底部出现大按钮**「就定周六下午」**；直接点高亮的「最多人有空」时段则按钮预选该时段。定档必须是显式确认，不做人数达标后自动锁定。

1. 该投票状态锁定为「已定档：周六下午」
2. 生成**定档结果卡片**，组织者一键分享回群：`「球局定了！周六下午 · 7 人有空」`
3. 该时段投过票的人自动成为**「到场名单」**，并写入该活动记录
4. 定档结果自动写入群日历，页面出现「看群日历」入口；openGid 获取失败时写入活动维度日历，不阻断收口
5. 「收点信息 / 分个工」按钮在 v1.0 仅作预告，分别到 v1.3 / v1.4 开通后直通创建页，并预填标题、日期与到场名单

定档后未选中时段的人看到：「这次时间没凑上，下次早点投」+ 该投票的「发起人主页」入口（转化为新组织者）。

#### 5.2.5 不设截止时间的默认行为

- 组织者可不设截止；此时定档按钮始终可用（人数最多的时段实时变化，徽标跟随）
- 沉默 72 小时无人投票的投票，详情页给组织者展示「催投」入口（订阅消息 + 复制催投话术，频控见 §10）

### 5.3 类型 B：单选投票「大家拿主意」（v1.2）

轻量表决：吃什么、去哪、看哪场。

- 组织者：标题 + ≤6 个选项（文字，每个 ≤12 字），可选设截止
- 群友：点一个选项即投（1 次点击），可改票
- 实名制：每个选项下直接显示投票者头像（协作场景要的就是"谁投了什么"，不做匿名）
- 结果：横条 + 票数 + 领先项徽标；组织者可「定这个」锁定并生成结果卡片
- 多选投票（每人可选 N 项）观察后再排期——先验证单选是否真的补足了组织场景

### 5.4 传播回路设计

| 触点 | 卡片 | 目的 |
|---|---|---|
| 创建后 | 发起卡片（已投 1 人） | 冷启动进入群 |
| 投票后 | 参与者页面常驻「分享到群」 | 名单更新的围观价值 |
| 定档时 | 结果卡片（定档 + 人数） | 第二次全群触达 |
| 进日历后 | 日历入口卡 / 周计划卡（v1.1） | 把"这一次"变成"这个群的安排" |
| 名单空隙 | 详情页内「我也发起一个」入口 | 参与者 → 新组织者的转化（病毒核心） |

## 7. 功能详述 · AI 高情商回复（迁企业主体后接入）

> ⚠ **个人主体不可上线本功能（决策 D4，2026-09 经微信官方类目文档确认）**：AI 生成内容类目仅开放非个人主体，且需《互联网信息服务算法备案》（生成合成类）或已备案第三方大模型 + 双方合作协议。本功能整体移至 **v2.x 迁移企业主体之后**，作为该阶段的增长与变现弹药；MVP 实验不含本功能。以下需求锚点保留，供迁主体后出详细交互增补。

### 7.1 核心流程

```
用户复制一段微信聊天内容 → 打开小程序（或从群卡片进入）→ 粘贴 → 选场景与语气 → 生成 3 条备选 → 点选复制 → 回微信粘贴发送
```

- 场景预设（单选）：`领导消息 / 长辈关心 / 朋友求助 / 婉拒 / 道歉 / 通用`
- 语气预设（单选）：`高情商 / 委婉拒绝 / 幽默化解 / 简洁正式`
- 生成 3 条备选，「换一批」可再生成（限 5 次/天，控成本）
- 结果一键复制，附「回到微信」引导

### 7.2 约束

- 输入内容过内容安全接口（用户输入不可控，必须有 UGC 防御）
- 生成内容输出前同样过审核（LLM 生成结果不可直接信任）
- 每日免费额度 3 次，看激励视频 +5 次（变现主设计，见 §14.3）；MVP 实验期全免费且不展示广告
- 明示「内容由 AI 生成，仅供参考」
- 不承诺"必回成功"类话术，不做情感咨询定位（避免心理类目审核问题）
- **前置条件（D4）**：迁移企业主体 + 算法备案（生成合成类），或接入已备案第三方大模型 API + 双方合作协议；AI 生成内容须显著标注「AI 生成」

### 7.3 为什么它是拉新钩子而不是留存功能

AI 回复是单人场景，用完即走、无回访动力，但它的使用现场天然带传播：回复得太妙会被问"你怎么这么会说话"。详情页在生成结果底部常驻一张转发卡片：`「这个回复小程序生成的，点我也能用」`。

## 7B. 功能详述 · v1.4 群待办/分工（凑分工）

### 7B.1 定位边界

群待办**不是通用 todo 工具**——单人待办没有群传播（不满足筛选标准①），且竞品遍地。它只做一件事：**一次群活动从"定了"到"成了"之间的分工认领**。

- 场景锚点：投票定档周六打球 → 紧接着三个问题冒出来：谁订场？谁带球？谁买水？——这三个问题回到群里又是刷屏接龙
- 和投票的关系是**上下游**：投票输出"何时何地多少人"，待办输出"每人认领什么"——从定档页一键发起，活动标题、到场名单自动带入
- 与通用 todo 的区别一句话：**待办挂在活动上，不挂在人上**。活动结束待办自动归档进群日历，不制造任何"待办焦虑"（不做逾期红点、不做个人任务中心——福签产品的"永不惩罚用户"原则同样适用：分工是帮忙，不是欠债）

### 7B.2 创建流程（发起人视角）

入口两条：
1. **主入口**：投票定档页 →「给这场分个工」大按钮（主链路延伸）
2. **独立入口**：首页「发起待办」（没经过投票的活动也能用）

创建（≤3 次点击 + 极少输入）：
1. 活动标题自动带入（「周六球局」），可改
2. **快速添加事项**：输入事项名（≤10 字，如"订场""带球""买水"），每项一个；系统预置高频事项模板一键带入（订场 / 买水 / 带装备 / 拍照 / 定餐厅）
3. 每项可选：限 1 人认领（默认）或多人可认领（如"买水"可 2 人）
4. 「创建并分享到群」

### 7B.3 认领流程（群友视角）

```
点开卡片 → 待办详情页（活动名 + 事项列表 + 谁认领了什么）
  → 对没被认领的事项点「我来」          ← 1 次点击，认领成立
  → 完成后回来点「搞定了」              ← 打钩
  → （可选）「分享到群」常驻
```

硬规范：
- 事项卡片三种状态一目了然：**空缺**（虚线铅笔框 +「我来」按钮）/ **已认领**（实名头像 + 荧光黄）/ **已完成**（打钩 + 灰化）
- 认领反馈即时：头像飞入事项卡（≤1s 动画）
- **可转让不可撤销**：认领后可「转给别人」放回池子，不许悄悄消失——群协作的信任靠实名
- 待办内容为 UGC，同投票标题走内容安全接口

### 7B.4 盯催（发起人视角）

- 看板：`5 个事项 · 已认领 2 · 已完成 1 · 空缺 2`
- 对空缺事项「催一下」：复制催办话术 + 卡片链接由发起人转发；订阅过的人发订阅提醒（频控同 §10：同人 ≤1 次/日、每事项 ≤3 次）
- 话术文案基调是"喊人搭把手"，禁止催债式句式

### 7B.5 结果卡与传播

| 触点 | 卡片 | 目的 |
|---|---|---|
| 创建后 | 待办卡（`周六球局 · 5 件事没人领`） | 冷启动进群 |
| 全部认领完 | 进度卡（`5 件事都有着落了`） | 第二次回群 |
| 全部完成后 | 完成卡（`周六球局 · 5 件事全办成了`） | 收口，沉淀进群日历 |

**「还差谁」清单是待办的传播物**：空缺状态本身有紧迫感（球没人带、场没人订），驱动发起人把卡发回群里——这是待办功能自带的传播回路，与 V2 洞察（结果卡=通知）一致。

## 7C. 功能详述 · 群日历（v1.0 基础，v1.1 增强）

### 7C.1 定位边界

群日历不是投票后的附属展示，而是 v1.0 的留存层：**把"这一场什么时候"升级为"这个群接下来和历史"**。定位分两档：

- **v1.0 基础日历**：定档自动写入、顶部「接下来」、月视图、历史活动、活动详情、「照这场再约一次」。openGid 获取失败时降级为活动维度历史，不阻断主链路
- **v1.1 日历增强**：活动提醒、周计划卡、群节奏（常用时段 / 常来的人）、规则化建议时段、月度战功卡
- **载体优先是群，不是人**：能拿到 openGid 时，日历挂在群维度；拿不到时挂在活动维度。不做个人打卡、不做个人任务中心，避免把群体协作变成个人压力
- **主视图 = 月日历，不做信息流**：一个月 4-6 场活动的密度撑不起 feed 流；月格子一屏看完整月，点日子再看详情。「整月活动列表」只作为次要入口
- **个人主体可做**（工具-日历/备忘录类目对个人开放），且必须随 v1.0 上线：没有日历，投票就只是单次工具，第一次使用后没有自然回访理由

### 7C.2 月视图交互（定稿）

```
┌─────────────────────────────┐
│ 接下来：周六球局 · 7 人     │
│ ‹    2026 年 9 月    ›      │  月份翻页
│ 一  二  三  四  五  六  日  │
│     ①  ②  ③  ④  ⑤  ⑥   │  有定档活动的格子点亮
│ ⑦  ⑧  ⑨ ⑩ ⑪ [12] ...      │  + 协作小点（见下）
└─────────────────────────────┘
    ↓ 点任意日子，下半屏展开该日详情
```

- **协作小点**：每格右下角一排小点——蓝点=走过时间投票、绿点=走过收集填表、金点=走过群待办。活动密度和协作深度不用点开就能扫出来；格子内不写活动名缩写，避免单日多活动时拥挤
- **选中态**：点日子 → 下半屏显示该日活动卡（活动名 / 定档时间 / 到场名单 / 投票快照 / 收集与待办徽标），点卡回看该场详情
- **空日召唤**：无活动的日子点开显示 `「这天还没安排，约一场？」`，按钮直通时间投票创建页并预填该日期——空格是发起入口，不是空白状态
- **历史活动卡**：已完成活动保留「照这场再约一次」，一键创建新时间投票，预填标题、活动模板、常用候选时段；不自动拉人、不自动发消息，仍由组织者确认分享
- **今天**记号蓝描边；顶部「接下来」最多展示 2 场，避免日历首屏被列表淹没

### 7C.3 v1.1 日历增强：群节奏与复用

群节奏是把群资产变成下一次发起效率的核心创新，全部使用规则统计，不调用 AI、不生成内容：

- **常用时段**：根据本群已定档活动与投票结果，展示 Top 3 时段（如「周六下午 · 最近 4 场有 3 场」）；创建投票时可一键带入
- **常来的人**：展示本群最近参与过活动的成员头像，用于组织者心里有底；不做缺席名单、不做个人排行、不显示"谁没来"
- **规则化建议时段**：创建时给组织者推荐 3 个候选时段，依据是本群历史成功率、节假日与发起时间；页面标注「根据本群历史推荐」
- **模板库分层**：v1.0 提供静态模板（球局 / 聚餐 / 爬山 / 桌游），v1.1 升级为「本群常用模板」——标题、候选时段、备注可一键复用

### 7C.4 v1.1 提醒与传播卡

- **活动提醒**：定档后在投票详情页与日历页请求一次性订阅，活动前一天提醒；提醒预算与催投、待办提醒共享 §10 频控，不做多渠道轰炸
- **周计划卡**：周一可生成「本周安排」卡片（N 场活动 + 日期 + 组织者署名），由用户主动分享回群，让日历从回访页变成第二次传播触点
- **月度战功卡**：月底生成事实型战功卡（N 场活动 · N 人次参与 · N 场完整链路），不做虚构评分、不做群排名；这是组织者的成绩单，也是群集体记忆的传播物
- **完整链路标记**：一场活动走满「定时间 → 收信息 → 分工」标为完整链路，只走过投票标为半程；标记只用于展示协作深度，不产生奖励、惩罚或解锁依赖

## 9. 增长实验：100 群跑一周

### 9.1 实验设计

| 项 | 内容 |
|---|---|
| 规模 | 100 个真实群（自有/种子用户自带） |
| 群类型配额 | 同学/老友群 40 · 兴趣活动群（球局/爬山/桌游）30 · 家庭/亲戚群 15 · 拼团/团购群 15 |
| 周期 | 7 天 |
| 操盘 | 种子群主一对一引导发起第一个时间投票（人工冷启动，不做任何投放） |

### 9.2 实验指标与成功线

| 指标 | 定义 | 及格线 | 良好线 |
|---|---|---|---|
| 群参与率 | 种子投票发出后，≥3 人参与的群占比 | 50% | 70% |
| 二次发起率 | 7 天内发起第 2 个活动的群占比 | 25% | 40% |
| 分享率（核心） | 参与用户中把任意卡片再分享到群的比例 | 20% | 35% |
| 次日留存 | 参与用户 D1 回访率 | 20% | 30% |
| 日历回访率（核心） | 参与或查看定档结果后 7 天内进入群日历的用户占比 | 15% | 30% |
| 从日历发起占比 | 新活动中由「照这场再约一次」或日历入口创建的比例 | 10% | 25% |
| 14 天复约率（核心） | 已定档群在 14 天内再次定档的比例（实验结束后第 14 天补算） | 20% | 35% |
| 自然新群 | 非种子群主自发发起的自然群数 | 10 | 30 |
| 定档转化率 | 已有投票中最终被组织者「定档」的比例（验证投票收口价值） | 40% | 60% |

**实验结论三选一**：
- ≥ 良好线 → 加速：推进 v1.1 日历增强（提醒 / 复用 / 周计划卡）+ v1.2 单选投票
- 及格~良好 → 拆解瓶颈场景（定档率低→收口交互改；日历回访低→入口与提醒改；复约低→再约路径改），单点迭代再跑两周
- < 及格线 → 复盘传播与定档链路断点（卡片设计 or 群主动力），大改后重跑

### 9.3 传播设计（病毒公式与抓手）

群工具的裂变与普通产品不同：普通产品 1:1（我分享给你），群工具是 **1:N**（我发一张卡片，全群所有人都看得到且都有理由点开）。病毒系数：

```
K = 每个活动带来的新用户
  = 群人数 × 卡片点开率 × （参与者成为新组织者的转化率 × 他自己的群数）
```

前三环（卡片直达、≤2 次点击参与、定档卡）由功能设计保证，真正决定量级的是三个设计洞察：

| # | 洞察 | 设计落点 |
|---|---|---|
| V1 | **组织者是唯一的传播节点，给他「面子」**——没人为了工具发起活动，人是为了当"把事张罗成的那个人" | 定档卡片署名：`「球局定了！周六下午 · 王哥组织的」`——这张卡在群里就是王哥的功劳榜；群主页给组织者攒战功（本周组织 2 场、张罗过 8 次聚餐），是他的社交货币 |
| V2 | **结果卡片是「通知」，不是「广告」**——定档卡、周计划卡承载全群都需要的真实信息，转发的心理阻力为零 | 每次使用自然产出 1-2 张"必须回群"的卡片（定档卡、周计划卡、月度战功卡）；分享率不是运营出来的，是功能里长出来的 |
| V3 | **每个参与者都是潜在新组织者** | 投票详情页常驻「我也发起一个」入口；参与者转化在自己的其他群再发卡，形成链式触达 |

冷启动抓手（零预算，个人主体现实）：

- **微信搜一搜 SEO**：小程序名与简介埋「投票 凑时间 聚餐 定时间 接龙」关键词——"聚餐怎么定时间"是真有人在微信里搜的，这是免费的量
- **节日模板钩子**：五一去哪玩、端午聚餐、年会时间——节日前一周是天然发起高峰，提前备好一键模板
- **发起时机运营**：周四是发起高峰（大家约周末），种子群主统一在周三/四晚发卡
- 现实预期：不买量不投放。实验指标「自然新群 ≥10」就是爆火假设（V3 链式传播成立）的第一次验证

## 10. 合规红线（一票否决项）

1. **不碰资金**：资金协作功能已整体砍除（D5），产品内无任何资金相关界面与文案；用户自行使用微信原生「群收款」
2. **不诱导分享**：功能不依赖分享解锁；分享按钮无利益承诺文案
3. **内容安全**：投票标题/选项/备注为 UGC，提交前过微信内容安全接口；AI 回复输入输出双向过审
4. **订阅消息频控**：全部订阅类触达 ≤ 1 条/人/日；催投与活动提醒同活动同人合计 ≤ 3 次，且仅发给已订阅用户
5. **隐私最小化**：仅采集 openid（静默）+ 用户主动授权的昵称头像 + 业务数据；**无手机号、无位置**（与竞品拉开差距的卖点：用竞品投票先要手机号，用我们什么都不用给）
6. **AI 声明**：AI 生成内容明示来源与"仅供参考"，不做心理/医疗建议；个人主体下 AI 功能的类目合规先确认再开发
7. **群数据边界**：openGid 群内所有成员可见该群聚合数据（活动名单本来即群内公开信息）；不向群外暴露

## 11. Roadmap：从定时间到管事情的群协作链路

产品叙事见 §1.3：**定时间（投票）→ 管事情（群日历）→ 凑人头（收集填表）→ 凑分工（群待办）**。每个版本给链路加一段，每个环节的产出是下一环节的输入。功能优先级筛选标准：① 长在群协作上（1:N 传播）；② 有"汇总者痛点"（为组织者省人肉活）；③ 有"值得回群的结果卡"（C1 约束下的传播闭环）。不满足三条的功能不进 Roadmap（群聊总结、签到打卡、匿名吐槽等已按此标准排除，见 §4.2）。

| 版本 | 功能 | 链路位置 | 关键设计点 |
|---|---|---|---|
| v1.0（MVP） | 时间投票 + 定档 + 基础群日历 | **定时间 / 管事情** | 多选可用时间聚合、最优时段高亮、一键定档；定档自动写入日历，日历承接「接下来 / 历史活动 / 再约一次」 |
| v1.1 | 日历增强 | **管事情** | 活动提醒、订阅消息、周计划卡、月度战功卡、群节奏建议、规则化推荐时段；功能详述见 §7C |
| v1.2 | 单选投票「大家拿主意」 | **扩场景** | 与时间投票共用活动、参与者、分享、汇总底座；先验证时间投票 + 日历闭环，再扩展快速表决 |
| v1.3 | 收集填表 | **凑人头** | 自定义字段表单（报名表/信息收集）：群主定义字段 → 群友点卡片填 → 自动汇总、一键导出名单；**被砍的「接龙」以最简收集模板形态在此回归**（+1 报名即单字段收集） |

## 14. 变现策略

### 14.1 总原则

- **MVP 实验期（W1-W5）：零广告零变现。** 工具冷启动阶段广告直接伤参与率与分享率，实验数据会被污染；变现弹药位只做预留（埋点/额度系统），不上线任何广告代码
- **个人主体的变现现实**：不可开通微信支付（C3/D1），所以 MVP+ 阶段唯一可行通道是**流量主广告**（不受主体限制）；会员/付费等交易类变现全部押后到迁移企业主体之后
- 优先级永远：**实验指标（分享率/留存/复约率）> 广告收入**。广告位只允许出现在非主路径页面

### 14.2 流量主广告位规划（MVP 实验通过后逐步上线）

| 广告位 | 形式 | 上线时机 | 原则 |
|---|---|---|---|
| 投票结果页底部 | banner | 实验通过后首批 | 结果已看完，不打扰主路径 |
| **AI 回复「次数用完了」** | **激励视频（主力变现位）** | **v2.x 迁企业主体后**（随 AI 回复，D4） | 用户在"我要用"的临界点，工具产品中转化率最高的广告形式 |

### 14.3 变现主力的变更：AI 回复随 D4 移至 v2.x

- 原设计「AI 回复 + 激励视频」（免费 3 次/日，看视频 +5 次，替代内购）随 AI 回复一并移至 v2.x 迁企业主体之后
- **迁移前的变现主力只剩 banner / 插屏**——天花板显著变低：投票与日历是低时长工具，广告 eCPM 靠曝光量堆，规模化之前月收入量级仅为百元级。这是个人主体决策（D1）+ AI 合规现实（D4）叠加的真实代价，**接受它**：用 MVP 实验数据（分享率/留存/自然新群/复约率）决定是否值得迁企业主体，把 AI 变现、Pro 订阅等商业化路径一起解锁
- v2.x 接入 AI 时，额度系统（免费 3/日 + 视频奖励）一次做进后端，避免后期改账本结构；`ad_watch` 埋点同期就绪（§9.4）

### 14.4 明确不做的变现

- ❌ MVP 期放任何广告（污染实验）
- ❌ CPS/淘宝客/导购分佣（调性崩，工具心智不可逆受损）
- ❌ 卖群主会员（MVP 期；迁企业主体后评估「群主 Pro」：Excel 导出、无限模板、更长活动历史）
- ❌ 资金类抽成（资金功能永久不做，D5/C3）

### 14.5 变现 Roadmap

| 阶段 | 通道 | 前提 |
|---|---|---|
| MVP 实验期 | 无（零广告） | — |
| 实验通过 + DAU 起量 | banner / 插屏（变现主力，天花板百元级/月） | 流量主开通门槛达标 |
| v2.0+（迁企业主体） | **AI 回复激励视频**（新的变现主力）+ 群主 Pro 订阅 | 企业主体 + 算法备案或已备案大模型 API（D4）+ 微信支付商户号 + 资质评估 |
