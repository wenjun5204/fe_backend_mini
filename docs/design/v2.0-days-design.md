## 1. 后端设计（backend/，原地演进）

### 1.1 数据库变更（JPA ddl-auto=update 增量建表，双 profile 自动兼容）

无 ALTER，仅新增两表。对齐 `BirthdayRecordEntity`/`BirthdayReminderEntity` 的 JPA 注解风格（`@Table` + `@UniqueConstraint` + `@Enumerated(EnumType.STRING)`）。

**`day_record`（DayRecordEntity）**

| 列 | 类型 | 约束 | 说明 |
|---|---|---|---|
| id | BIGINT IDENTITY | PK | |
| user_id | BIGINT | NOT NULL, `idx_day_user` | 创建人 |
| family_id | BIGINT | NULL, `idx_day_family` | 创建人当时所属家族快照；**无家族用户为 NULL**（每人限 1 家族、MVP 无换族，快照即当前值） |
| relation | VARCHAR(12) | NOT NULL | 关系文本 1-12 字 |
| emoji | VARCHAR(8) | NOT NULL | 1 个表情；缺省由 relation 预置映射，自定义 😊 |
| kind | VARCHAR(16) | NOT NULL | BIRTHDAY / ANNIVERSARY / TOGETHER |
| calendar_type | VARCHAR(8) | NOT NULL | SOLAR / LUNAR；TOGETHER 固定 SOLAR |
| day_month | INT | NOT NULL | 1-12；TOGETHER 冗余存起始日当月 |
| day_day | INT | NOT NULL | 1-31；TOGETHER 冗余存起始日当日 |
| visibility | VARCHAR(8) | NOT NULL | FAMILY / PRIVATE |
| created_at | TIMESTAMP | NOT NULL | TOGETHER 完整起始日 = createdAt 的年 + month/day（决策 D1 无年份字段） |

**`day_reminder`（DayReminderEntity）**

| 列 | 类型 | 约束 | 说明 |
|---|---|---|---|
| id | BIGINT IDENTITY | PK | |
| day_id | BIGINT | NOT NULL | 属主行 |
| user_id | BIGINT | NOT NULL | 配置人（per-user，决策 D3） |

### 1.2 Repository

`DayRecordRepository extends JpaRepository<DayRecordEntity, Long>`：

```java
/** 可见集合：本人全部 + 同家族他人 FAMILY（无家族时只传 userId，familyId 传 null 用 :familyId is null 分支） */
@Query("SELECT d FROM DayRecordEntity d WHERE d.userId = :userId " +
       "OR (d.familyId = :familyId AND d.visibility = 'FAMILY')")
List<DayRecordEntity> findVisible(@Param("userId") Long userId, @Param("familyId") Long familyId);
```

无家族用户：`findVisible(userId, null)`，null familyId 使 FAMILY 分支永不命中，等价只查本人——满足「未加入家族强制 PRIVATE」的读取侧。

`DayReminderRepository extends JpaRepository<DayReminderEntity, Long>`：

```java
Optional<DayReminderEntity> findByDayIdAndUserId(Long dayId, Long userId);
void deleteByDayId(Long dayId);                        // 删除日子时清全部家人的提醒行（参照 deleteByBirthdayId）
List<DayReminderEntity> findByRemindersNot(String empty);  // reminder-due 扫描：reminders <> ''
```

MVP 数据量级（个人/家族级几十行）沿用生日簿「全量拉取 + 内存计算/排序」策略，不分页。

### 1.3 公农历换算复用策略（LUNAR 落点核心）

现状：**无独立 CalendarConvertService**。换算核心是 `BirthdayService` 的私有方法群，基于 `net.time4j.ChineseCalendar`：

- `nextDate(CalendarType, month, day, isLeapMonth)` — 下次落点主入口（SOLAR：今年候选、过期则 +1 年；LUNAR：today-1 年 ~ today+2 年窗口逐年试 `lunarCandidate`）
- `solarCandidate(year, month, day)` — 2 月 29 平年降 2 月 28
- `lunarCandidate(year, month, day, isLeapMonth)` — 某农历年月日的公历落点，不存在返回 null
- `lunarText(ChineseCalendar)` — 「农历八月十五」显示文本；`chineseDate`/`fromChineseDate` — time4j 双向转换

**方案：抽公共核心类 `service/CalendarConvertCore.java`（包内静态工具，无状态）**，把上述 6 个私有方法上移为 public static；`BirthdayService` 改为委托调用（行为不变，`BirthdayServiceTest` 既有用例回归护栏）；`DayService` 直接复用同一核心。不选 DayService 调 BirthdayService 的跨服务耦合，也不复制粘贴两份换算逻辑（农历落点 bug 必须单点修）。

DayService 侧口径（决策 D5：不暴露闰月）：

- LUNAR 落点 = `CalendarConvertCore.nextDate(LUNAR, month, day, false)`（仅按平常月/日数值匹配；窗口内逐年试非闰月，全部不存在则 40000）。
- `nextDateLunarText` = 落点公历日期经 `lunarText` 生成（SOLAR/LUNAR 两口径统一用落点反查文本，SOLAR 日子顺带得到「农历九月廿六」副文本）。
- 录入页实时换算走既有 `POST /api/calendar/convert`（DTO/端点零改动），DayService 不另开换算接口。

### 1.4 DayService

新建 `service/DayService.java`，风格对齐 `BirthdayService`（构造注入、私有校验方法、`ApiException` 抛错、DTO 组装方法 `toDto`）。核心规则：

**身份与家族**

- `CurrentUser.get()` 取 userId；`familyMemberRepository.findByUserId(userId)` 得 **Optional**（与生日簿不同：**无家族用户不拦截**，生日簿 `requireMember` 抛 40900 的模式不搬）。
- 无家族 → `familyId=null`；请求传 `visibility=FAMILY` 时**服务端降级为 PRIVATE**（契约 DayVisibility 语义），有响应可见性可解释，非报错。
- 权限模型（对齐生日簿）：`canView = 自己创建 OR (同家族 AND visibility=FAMILY)`；`canEdit = 自己创建 OR (同家族 AND FAMILY 可见 AND 本人 role=OWNER 户主)`。越权一律 `ApiException.notFound("没有找到这条日子")`——40400 等价不存在，不泄露存在性（契约 404 语义）。

**校验（40000，全在 service 层，不依赖注解）**

- `relation`：非空、trim 后 1-12 字，否则「请您把称呼填写完整」。
- `kind`/`calendarType`/`visibility`：枚举非空。
- `kind=TOGETHER`：`calendarType` 强制 SOLAR（传 LUNAR → 40000「在一起的日子按公历记录」）；month/day 可省，服务端取 `LocalDate.now()` 写入冗余列。
- `kind≠TOGETHER`：month/day 必填；合法性**由换算核心兜底校验**——SOLAR 走 `solarCandidate`（2 月 30/31、4 月 31 等抛 40000；2 月 29 合法，落点平年自动降 28）；LUNAR 限 month 1-12、day 1-30（原型下拉固定 30 项），落点窗口试不中 → 40000。
- `emoji`：可空；空则按 relation 预置映射（妈妈=👩 / 爸爸=👨 / 老伴=👴 / 儿子=🧑 / 女儿=👧 / 孙子=👦 / 孙女=👧 / 亲家=🤝 / 我自己=😊，与前端 `days-data.js` 同表双端各持一份），自定义关系默认 😊。
- `reminders`（仅 POST 生效，PUT 忽略）：⊆{7,3,0}、去重、≤3 项，违者 40000「提醒时间只能选择提前 7 天、3 天或当天」——校验逻辑与 `BirthdayService.normalizeReminderDays` 同款。

**计算字段（`toDto` 组装，只读不落库）**

- `nextDate`：非 TOGETHER 走换算核心；TOGETHER 为 null。
- `daysUntil = ChronoUnit.DAYS.between(LocalDate.now(), nextDate)`，≥0（落点构造保证不早于今天；0=就是今天）。
- `togetherDays = max(1, ChronoUnit.DAYS.between(起始LocalDate, today))`，起始 LocalDate = `createdAt.toLocalDate()`（month/day 冗余列与之一致，仅为展示冗余）；仅 TOGETHER，其余 null。
- `reminders`：当前用户视角——`dayReminderRepository.findByDayIdAndUserId` CSV 解析（同 `BirthdayService.splitReminderDays`）。

**7 个服务方法与事务（MySQL 严格模式铁律：`@Transactional(readOnly=true)` 内零写库，无兜底 save）**

| 方法 | 事务 | 逻辑要点 |
|---|---|---|
| `getDays()` | `@Transactional(readOnly=true)` | `findVisible(userId, familyId)` → 逐条 `toDto` → 排序：非 TOGETHER 按 daysUntil 升序在前，TOGETHER 固定底部（对齐原型 `renderDays` 排序，服务端排好，前端直接渲染） |
| `create(req)` | `@Transactional` | 校验→落 familyId 快照→visibility 无家族降级→save 记录→reminders 非空时落 `day_reminder`（dayId+userId）→返回 `toDto` |
| `getDay(id)` | `@Transactional(readOnly=true)` | `findById` + `canView` 过滤，不可见/不存在 → 40400 |
| `update(id, req)` | `@Transactional` | `findById` + `canEdit`（40400）→ 校验（忽略 reminders 字段）→ 全量覆盖式 apply→save→`toDto`；无家族用户编辑旧 FAMILY 记录按 PRIVATE 处理无影响 |
| `delete(id)` | `@Transactional` | `canEdit`（40400）→ `dayReminderRepository.deleteByDayId(id)`（清**全部**家人的提醒行，日子不存在则提醒停止，对齐生日簿 `deleteByBirthdayId`）→ `delete` → `{deleted:true}` |
| `updateReminder(id, req)` | `@Transactional` | `canView`（不可见 40400，含他人 PRIVATE）→ 校验 reminders → `findByDayIdAndUserId().orElseGet(新建)` 覆盖式 save（幂等）→ 回显 `{dayId, reminders}` |
| `getReminderDue(date?)` | `@Transactional(readOnly=true)` | date 缺省今天，yyyy-MM-dd 解析失败 40000；`findByRemindersNot("")` 全量提醒行 → 对每行：加载 day→按 date 计算 daysUntil（同款换算核心，基准日换成给定 date）→ 命中用户 CSV 中某 offset 即产出一条 `DayReminderDueItem{dayId, userId, remindOffset, title="妈妈的生日", actionText(≤24 字,按 kind×offset 预置文案库), kind, relation, daysTo, daysSince}`。**本端点不截断**：返回全部命中项，`total=items.size`；「≤3 条/人/天」频控在 Stage 9 发送链路按 userId 截断（需求 D4 交付边界；NotifyService 现行 4 条/天额度账本不变，「日子提醒」模板日上限 3 在发送侧配置） |

### 1.5 Controller（`ApiController` 新增 7 路由）

沿用单 controller 薄委托风格（构造注入 `DayService`，方法一行委托，类头注释 25→32 个 operationId 同步更新）：

```java
@GetMapping("/days")                     listDays()                          → DayListResponse
@PostMapping("/days")                    createDay(@RequestBody DayUpsertRequest)
@GetMapping("/days/{id}")                getDay(@PathVariable Long id)
@PutMapping("/days/{id}")                updateDay(@PathVariable Long id, @RequestBody DayUpsertRequest)
@DeleteMapping("/days/{id}")             deleteDay(@PathVariable Long id)
@PutMapping("/days/{id}/reminder")       updateDayReminder(@PathVariable Long id, @RequestBody DayReminderRequest)
@GetMapping("/days/reminder-due")        getReminderDue(@RequestParam(value="date", required=false) String date)
```

路由冲突说明：Spring MVC 精确路径（`/days/reminder-due`）优先于模板路径（`/days/{id}`），`{id}` 声明为 Long 亦无歧义；GET 与 PUT 语义分离，无需特判。

### 1.6 DTO（契约骨架生成 → 人工整合路径）

- 契约 codegen 从 `api/openapi.yaml` tag=days 生成 DTO 骨架（harness Stage 4 产物，落 `backend/target/generated-sources` 或临时目录）。
- **人工整合路径**：新建 `backend/src/main/java/com/example/backend/dto/DayDtos.java`，按 `BirthdayDtos.java` 的分组风格改写骨架——`final class DayDtos` + 私有构造 + 嵌套 `public static class`（getter/setter 单行体）+ 嵌套枚举 `DayKind{BIRTHDAY,ANNIVERSARY,TOGETHER}`、`DayVisibility{FAMILY,PRIVATE}`。

### 2.4 数据流

**登录 → 列表渲染**

```
App onLaunch(wx.cloud.init)
 → days 页 onShow: ensureLogin()  ── 云通道 callContainer 自动注入 X-WX-OPENID,body 空
                                   └─ 本地通道:dev-openid 作 code(同旧 request.js)
   → POST /api/auth/login → {token} 存 'njs_token'
 → GET /api/days → items(服务端已排序:daysUntil 升序,TOGETHER 底部)
 → renderDays: hero=items 首个非 TOGETHER;逐行渲染倒计时/相伴天数;空数组走空状态
```

**记日子（创建）**：add 页零键盘收集 → 月日联动（SOLAR 按月天数 28-31、LUNAR 固定 30 项）→ 每次选择变化调 `POST /api/calendar/convert` 实时显示对侧文本 +「X 天后」（kind=TOGETHER 时整块日期区隐藏）→ 提醒开关首次开启弹授权说明（发送内容/每日最多 3 条/只发给自己）→ 允许：`wx.requestSubscribeMessage` → `POST /api/notify/subscribe`（模板 ID 占位）→ `POST /api/days`（带 reminders）→ 成功 toast「日子记好了」→ 直达详情页；拒绝：提醒保持关闭（不调接口，功能不受影响）。

**编辑/删除**：详情页 `PUT /api/days/{id}`（全量覆盖，reminders 不随行）→ 刷新详情；删除 `wx.showModal` 二次确认（提示「提醒也会停止」）→ `DELETE /api/days/{id}` → 返回首页 onShow 重拉。

**提醒配置**：详情页开关/全部日子页入口 → 与创建同款授权弹层 → 允许：`wx.requestSubscribeMessage` + `POST /api/notify/subscribe` + `PUT /api/days/{id}/reminder` 回显配置；关闭/拒绝：`PUT .../reminder` 传 `[]` 或不调（开关态以服务端回显为准）。`/api/days/reminder-due` 小程序端**不调用**（服务端调度/Stage 9 联调用）。

**全部日子页**：时间线视图 = 列表数据按 `nextDate` 月份分组 +「N 个日子」分组头，TOGETHER 归「每天 · 相伴中」组；日历视图本地渲染（月切换 `calMove`），**仅标记 `userId` 为自己的日子**（生日/纪念日各一色点，不标公共节假日），点有日子的日期弹当日事件清单 → 进详情。

## 4. 风险与对策

| 风险 | 对策 |
|---|---|
| 新旧小程序同 AppID 共享 wx storage，token key 冲突导致互踢登录态 | 新目录 TOKEN_KEY/USER_KEY 独立命名（`njs_*`），上线改名过审后旧目录移 legacy |
